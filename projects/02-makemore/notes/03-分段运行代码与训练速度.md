## 一、分段运行：三种方案

### ★ 方案 A：VS Code 的 `# %%` 单元格（推荐）

**不用装任何插件**——VS Code 的 Python 扩展自带。

用法：

1. 在 `.py` 文件里用 `# %%` 分隔代码块
2. 光标放在某个块里，按 **`Shift+Enter`** 执行该块
3. **变量会保留在内存里**，改一块只重跑那一块

```python
# %%
import torch
from torch.nn import functional as F
# ↑ Shift+Enter 执行

# %%
names = open("names.txt").read().splitlines()
# ↑ 单独执行，names 留在内存里

# %%
for i in range(100000):
    ...
# ↑ 训练只跑一次

# %%
emb = C[Xtr]
loss = ...
print(loss)
# ↑ 这部分可以反复改、反复跑，不用重训！
```

**为什么最适合本项目**：

`mlp_test.py` 里「训练」和「评估」是分开的两段。用单元格跑一次训练，
然后评估部分可以随便改、随便重跑——这是最大的省时间点。

**优点**：
- 零安装（你的系统已有 `ipykernel`）
- **文件仍然是 `.py`，git diff 正常**
- 变量保留

### 方案 B：Jupyter Notebook（`.ipynb`）

```powershell
pip install notebook
jupyter notebook
```

Karpathy 的视频里就是用 `.ipynb` 讲的，你看到的"分段执行"就是这个。

**但是**：`.ipynb` 是 JSON 格式，**git diff 看不出来你改了什么**。
本仓库的 `.gitignore` 已经把 `*.ipynb` 排除掉了。

如果你要用 notebook，建议配合 `jupytext` 把它同步成 `.py` 再提交：

```powershell
pip install jupytext
jupytext --sync batch_normalization.ipynb    # 会生成同名的 .py
```

### 方案 C：VS Code 的 Interactive Window

命令面板（`Ctrl+Shift+P`）搜 `Jupyter: Create Interactive Window`。
输出显示在侧边，更像 notebook。和方案 A 操作方式一样。

## 二、训练速度实测

### 2.1 CPU vs GPU：**这个模型 GPU 反而更慢**

用 `bench_device.py` 实测（配置：block=3, emb=10, hidden=200, batch=64）：

| 设备 | 2000 步耗时 | 每步 | 10 万步预计 |
|---|---|---|---|
| **CPU** | 1.69s | **0.85 ms** | **1.4 分钟** |
| GPU (RTX 4070) | 3.63s | 1.81 ms | 3.0 分钟 |

**GPU 慢一倍。**

**原因**：模型只有约 4.5 万个参数、batch=64，每步的计算量太小，
GPU 的 kernel 启动开销（每步几十微秒 × 多次调用）超过了它能带来的并行收益。

**结论：这个练习不要往 GPU 方向优化。**
GPU 的收益要到模型大到一定程度（几百万参数以上、batch 几百以上）才显现。

### 2.2 逐项开销分析：`loss.item()` 几乎不花钱

用 `bench_bottleneck.py` 实测：

| 版本 | 每步 | 相对基准 |
|---|---|---|
| ① 基准 | 0.83 ms | — |
| ② + `losses.append(loss.item())` | 0.84 ms | 慢 1%（可忽略） |
| ③ + `lrses.append(lr)` | 0.84 ms | 可忽略 |

**我原本猜测 `loss.item()` 的同步开销很大，实测否定了这个猜测。**
在 CPU 上它只是取一个标量，没有 GPU 同步问题。

不过 `losses` / `lrses` 会一直增长：10 万步存 20 万个浮点数。
不慢，但白占内存。**想看 loss 曲线的话每 100 步记一次就够了**，曲线形状看不出区别。

### 2.3 一个容易被忽略的开销：末尾的整集评估

`mlp_test.py` 跑完训练后这三行：

```python
emb = C[Xtr]                              # ★ Xtr 有 20 万条
act = torch.tanh(emb.view(-1, ...) @ W1 + B1)
logits = act @ W2 + B2
```

**是拿整个训练集算一次 loss**，矩阵乘法规模比单步训练大几千倍。
虽然只做一次，但在慢机器上可能要几秒到几十秒。

快速迭代时可以改成只取一部分样本估算：

```python
with torch.no_grad():
    sub = torch.randperm(Xtr.shape[0])[:10000]     # 随机取 1 万条
    emb = C[Xtr[sub]]
    ...
```

### 2.4 如果实测确实很慢，怎么查

在训练循环外面包一层计时：

```python
import time
t0 = time.time()
for i in range(100000):
    ...
print(f"训练耗时 {time.time()-t0:.1f} 秒")
```

| 实测值 | 说明 |
|---|---|
| ~90 秒 | 正常（我的实测是 1.4 分钟） |
| 300 秒以上 | 机器被拖慢了，检查：笔记本是否插电源、后台是否有占用、是否有降频 |

## 三、其他可以加速的方向

| 方法 | 效果 | 代价 |
|---|---|---|
| 减少步数 | 线性加速 | loss 偏高 |
| 增大学习率 + 更少步数 | 可能等效 | 太大就不收敛 |
| 用 `torch.compile` | 理论上有加速 | **Windows 上不可用**（缺 Triton） |
| 减少评估频率 | 省一点点 | 曲线分辨率降低 |

> `torch.compile` 在 Windows 上会报 `TritonMissing`，
> 这个坑在 `projects/03-nanogpt/notes/01-环境与网络实录.md` 里有记录。
