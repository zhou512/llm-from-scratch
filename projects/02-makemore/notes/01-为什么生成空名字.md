# 笔记 01 · 为什么 MLP 生成的是一堆空名字和「..」

> 背景：跟着 nn-zero-to-hero 第三讲写的 `mlp_test.py`（`projects/02-makemore/`），
> 输出里大量出现空行和「..」，看起来像是模型预测了训练数据里从没出现过的模式。
>
> 复现脚本：`diagnose_token_design.py`（自包含，约 2 分钟跑完）

---

## 一、先说结论：你的观察是对的，但机制比你想的多一层

你的猜测「训练样本里应该没出现过前三个字符都是 `.`、下一个还是 `.`」——
**完全正确**。但真正的原因是：

> **`.` 这个符号同时承担了三个角色：填充、开头标记、结尾标记。**
> 三种语境用了同一个符号，模型无法区分，于是学到了一个错误的分布。

---

## 二、`build_dataset` 里到底发生了什么

`mlp_test.py` 的做法：

```python
ctoi["."] = 0                                    # '.' 编号 0
names[i] = '.' + names[i] + '.'                  # 加首尾标记
context = blocksize * [0]                        # ★ 用同一个 0 做填充
```

**注意最后一行**：填充用的是 `0`，而 `0` 就是 `.`。所以三种语境全是 `0`：

| 语境 | 表示 |
|---|---|
| 名字还没开始（填充） | `.` (0) |
| 名字开始 | `.` (0) |
| 名字结束 | `.` (0) |

### 一个具体的名字看完整过程

以 `emma` 为例，加标记后是 `.emma.`，长度 6。走一遍循环：

| 步 | 取值 | 当前 context | 记录样本 (context → 目标) |
|---|---|---|---|
| 0 | `.`(0) | `[0,0,0]` | `[0,0,0] → 0` ← **开头标记** |
| 1 | `e`(5) | `[0,0,0]` | `[0,0,0] → 5` ← 首字母 |
| 2 | `m`(13) | `[0,0,5]` | `[0,0,5] → 13` |
| 3 | `m`(13) | `[0,5,13]` | `[0,5,13] → 13` |
| 4 | `a`(1) | `[5,13,13]` | `[5,13,13] → 1` |
| 5 | `.`(0) | `[13,13,1]` | `[13,13,1] → 0` ← **结尾标记** |

**看第 0 步和第 1 步**：两步的 context 都是 `[0,0,0]`（因为窗口只滑了 1 位，
还有两个填充的 0 在），但**目标不同**——一个是「开头标记」，一个是「首字母」。

于是 `[0,0,0]` 这个上下文，在训练数据里对应了**两种互相矛盾的目标**。

---

## 三、实测数据：矛盾有多大

在 32033 个名字、260179 条训练样本上统计 `context = [0,0,0]`：

```
context=[0,0,0] 共 64,066 条样本
  目标是『.』（结尾/开头标记）的: 32,033 条  (50.0%)
  目标是字母的:                   32,033 条  (50.0%)
```

**正好对半分。** 为什么是 50%：

- 每个名字产生 **2 条** context=`[0,0,0]` 的样本
  （第 0 步的「开头标记」+ 第 1 步的「首字母」）
- 32033 个名字 × 2 = 64066 ✓
- 其中一半（32033 条）目标是 `.`

而且 `'..'` 在**字面意义**上确实从没出现过（名字最短也有 1 个字母），
但**在样本层面**，`. → .` 这种转移真实存在了 32033 次。

---

## 四、训练后的模型忠实地学到了这个矛盾

训练 30000 步后，给定初始上下文 `[., ., .]`，模型的预测：

```
P('.') = 0.5115      ← 一半概率直接输出「结束」
P('a') = 0.0626
P('k') = 0.0467
P('m') = 0.0397
...
```

**模型没有错，是数据有歧义。** 它学到的是训练数据的真实统计，
而训练数据的统计被错误的数据表示污染了。

生成时初始 context 就是 `[., ., .]`，所以：

```
约 51% 的概率 → 第一个字符就是 '.'  → 名字当场结束 → 空名字
约 49% 的概率 → 输出一个字母 → 名字开始
```

实测 200 次生成：**106 个名字长度 ≤ 2**（大部分是空字符串）。

---

## 五、雪上加霜：生成循环还有个逻辑 bug

```python
if ix == 0:
    if len(out) >= 2:
        break
    else:
        continue      # ★ 问题在这
```

`continue` 是「**跳过本次循环的剩余部分，进入下一次 while 迭代**」——
它**不会重置 `out` 和 `context`**。

于是当第一个字符就是 `.` 时：

1. `out = ['.']`，`len(out) = 1 < 2` → 走 `continue`
2. `context` 变成 `[., ., 0]`（残留状态）
3. 下一轮继续采样，`out` 变成 `['.', 'a']`，长度够了
4. 再采样一次 `.` → `break` → 打印出 `'..'` 之类

**这就是你看到的「连续两个点」的直接来源。**

正确的写法应该是重置状态重新生成：

```python
if ix == 0:
    if len(out) >= 2:
        break
    else:
        # 重新开始这个名字，而不是接着攒
        out = []
        context = [0] * BLOCK_SIZE
        continue
```

## 六、修复：三种特殊标记必须分开

问题的根源是**一个符号承担了多个角色**。修复方式是引入三个不同的 token：

| 标记 | 作用 | 建议符号 |
|---|---|---|
| 填充 | 序列开头、上下文不足时补位 | `<P>` |
| 开头 | 名字开始 | `<S>` |
| 结尾 | 名字结束 | `<E>` |

```python
vocab = ["<P>", "<S>", "<E>"] + sorted(set("".join(names)))
stoi = {c: i for i, c in enumerate(vocab)}

for n in names:
    seq = [stoi["<S>"]] + [stoi[c] for c in n] + [stoi["<E>"]]
    context = BLOCK_SIZE * [stoi["<P>"]]      # ★ 填充用 <P>
    for ix in seq:
        X.append(list(context))
        Y.append(ix)
        context = context[1:] + [ix]
```

### 实测对比（同一个 `diagnose_token_design.py` 跑的）

| | 方案 A（`.` 三角色） | 方案 D（三者分开） |
|---|---|---|
| 词表大小 | 27 | 29 |
| `context=[填充×3]` 的目标是「结尾」的比例 | **50.0%** | **0.0%** |
| 训练后 P(结束标记) | **0.5115** | **0.0000** |
| 200 次生成中长度 ≤ 2 | **106 个** | **0 个** |
| 生成样例 | `['', '', 'cal', '', 'zha', '', ...]` | `['rayiah', 'kaislaniya', 'jen', 'vika', ...]` |

方案 D 生成的名字：

```
rayiah, kaislaniya, nusolan, jen, ayliottlin, henziellaroseanna,
sson, wollianna, mahanvion, vika, ...
```

**全部是像样的名字，没有空串。**

### 一个中间方案的教训

只把「开头」和「结尾」分开（开头用 `.`，结尾用 `<E>`）是不够的：

```
词表 28（'.' -> 0, '<E>' -> 1）
训练后 P('<E>') = 0.0001      ← 空名字问题解决了 ✅
训练后 P('.')   = 0.5134      ← 但生成结果里出现 '.brie'、'..iya' ❌
```

因为**短名字的填充点本身就是 `.`**，导致 `[. . .] → .` 这种模式又出现了，
模型学会了「开头之后还可能跟一个开头」。
**必须把填充也分开，三个角色各自独立。**

## 七、为什么这个问题值得深挖

这不是「模型调参没调好」，而是**数据表示（data representation）的设计问题**。
它体现了一个通用原则：

> **任何进入模型的符号，都应该只承载一个明确的含义。**
> 一个符号承担多个角色时，模型无法区分这些语境，
> 只能学到它们的混合统计——看起来像「模型学坏了」，其实是数据在骗它。

这类问题在实际工程里非常常见，比如：

| 场景 | 类似的问题 |
|---|---|
| 文本分类 | 用空字符串同时表示「缺失」和「空值」 |
| 时间序列 | 用 0 同时表示「真实值为 0」和「数据缺失」 |
| 推荐系统 | 用 user_id=0 同时表示「游客」和「第一个用户」 |
| 对话模型 | 用同一个 token 表示「用户说完」和「模型该说了」 |

**修法都是同一个：给不同含义分配不同的符号。**

## 八、你原本的代码要改哪些地方

`mlp_test.py` 里需要动四处：

1. **词表构造**（第 29-32 行）：引入 `<P>` `<S>` `<E>` 三个标记

   ```python
   vocab = ["<P>", "<S>", "<E>"] + sorted(set("".join(names)))
   ctoi = {c: i for i, c in enumerate(vocab)}
   itoc = {i: c for c, i in ctoi.items()}
   CHAR_SIZE = len(vocab)        # 29
   ```

2. **加标记**（第 33-34 行）：开头用 `<S>`，结尾用 `<E>`

   ```python
   names = ["<S>" + n + "<E>" for n in names]
   ```

3. **`build_dataset`**（第 18 行）：填充用 `<P>`

   ```python
   context = blocksize * [ctoi["<P>"]]
   ```

4. **生成循环**（第 100、109-113 行）：初始 context 用 `<P>`，遇到 `<E>` 停止

   ```python
   context = [ctoi["<P>"]] * BLOCK_SIZE
   ...
   if ix == ctoi["<E>"]:
       break
   out.append(itoc[ix])
   ```

   注意：`<S>` `<P>` 理论上不会被采样出来，但如果出现了要跳过（`if ix in (ctoi["<P>"], ctoi["<S>"]): continue`）
